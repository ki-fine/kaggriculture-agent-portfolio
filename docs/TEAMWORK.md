# 三人协作：如何把不同方案整合成最终版本

我在三人团队中负责汇总思路和最终代码构建。协作的主要难点是让不同方案在同一套资金、工人和交易时序中工作，并建立共同的实验标准。

## 共同接口：把“好想法”变成可以整合的约束

团队方案需要明确它读哪些信息、占用哪些动作位置、消耗哪些资源，以及失败时如何回退。

- 生产路线负责种植、浇水、喂食、采收和运输等义务
- 决策层在公开观察和己方库存范围内选择策略与交易
- 已接纳的交易位置和资金安排需要受到保护
- 新改动先核对完整任务链，再进入候选／对照实验

这样可以讨论一个方案与现有系统是否兼容，而不仅讨论它在某个局部窗口的收益。

## 协作案例：市场排程和往返交易争用位置

在组合新增多单排程与既有往返交易时，新订单占用了已经接纳的交易位置。单独调整先后顺序后，仍有一处肥料时序出现“预计 +1、实际 −1098”的落差。

整合阶段按以下顺序定位与处理：

1. 保留失败回放，核对预测订单和最终执行订单
2. 将冲突落实到同商品交易组和订单位置
3. 对已接纳的往返交易商品提供整组位置保护
4. 复测 12 个保存的失败窗口，再检查完整对局的动作和现金

这个案例体现了跨模块接口对齐、失败复现和回归验证。最终报告将它作为过程证据，没有把一个局部修复直接等同于全面提升。

## 协作案例：保留不同方案，用证据作选择

R7、R8、R9 对应不同的策略想法。R8 尝试等待新店信息再种植；R9 尝试相对收益和稳健需求情景。两个研究版本都保留了实现和实验记录，最终选择仍是 R7。

选择依据包括实际激活、完整运行、净金币差及样本限制。零激活不算提升，动作一致只能说明保留原行为，运行健康也不能替代收益验证。这让团队可以继续提出大胆方案，同时在最终交付时作出明确取舍。

## 交接与版本管理

固定上游 commit、候选哈希和实验身份，减少“比较的不是同一版”这类沟通错误。

每次整合记录以下信息：

| 记录项 | 作用 |
|---|---|
| 模块来源与固定 commit | 对应队友提供的确切版本 |
| 候选源码与 SHA-256 | 对应实际测试程序 |
| 种子、对手、席位和运行标记 | 解释实验覆盖范围 |
| 接受／淘汰决定和失败原因 | 避免重复尝试已失败的方案 |
| 包内源码与提交回执 | 对应最终交付版本 |

公开材料采用脱敏路径和精简数据；完整队友程序保留在团队研究仓库。来源范围见 [CREDITS.md](CREDITS.md)。
